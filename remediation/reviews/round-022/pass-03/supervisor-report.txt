I'm reviewing every artifact in evidence group 3, the UI screen SVGs, storyboard SVGs, manifest, markdown index, Marp deck and generated HTML, as a design-only hostile pass with no score.

**Outcome.** The group is textually consistent across manifest, markdown, deck and HTML, but it carries four major defects. The self-contained slideshow displays no screen images. The failure screen depicts a Running badge. The ARC target listener has no management surface. The storyboards never depict the external agent they promise. Beyond those, many states and affordances are named but not specified, which matters because the deck's title slide declares screen, state and control IDs authoritative.

## Findings

**Major**

- **P3-01. The self-contained HTML renders raw image markdown instead of screens.** In `design-c4/docs/storyboards.html`, every step slide from section id 2 through section id 25 contains a paragraph whose text begins with the literal characters `![bg right:62% contain](data:image/svg+xml;base64,`. No slide section contains an `img` element, a `figure` element, or a `data-marpit-advanced-background` attribute, which Marp emits whenever a `bg` image is parsed. The editable source at `design-c4/storyboards/storyboard.md:19` uses a relative path, so a build step substituted a data URI before Marp ran. The observable defect is certain from the text alone. My explanation, stated as a hypothesis, is that markdown-it rejects `data:` link destinations except gif, png, jpeg and webp, so the SVG data URI failed link validation and the inline parser emitted the source text. Requirement 12 asks for a self-contained navigable HTML with local SVGs. Navigation works, but the deck shows base64 text where every screen should be.

`★ Insight ─────────────────────────────────────`
markdown-it ships a default `validateLink` that blocks `javascript:`, `vbscript:`, `file:` and `data:` destinations, then re-allows only a short raster image whitelist. An SVG data URI falls through that gate and the image syntax degrades silently to plain text, with no build error. Inlining assets should therefore happen after rendering, by rewriting the emitted HTML, or the engine must be configured to accept the URI. A validation receipt that only counts slides will never catch this class of failure.
`─────────────────────────────────────────────────`

- **P3-02. The failure screen contradicts its own status chip.** `design-c4/docs/screens/SCR10.svg` carries the chip `data-status-id="SCR10.STATUS"` reading `MCP Running · snapshot r8` while the same artboard's subtitle says `Service could not start` and its MCP service card says `Error / listener not ready` and `Admission closed`. The markdown index at `design-c4/docs/ui-screens-and-storyboards.md:3` states the chip and the Android notification use the same HealthSnapshot revision, and the manifest's `shared_status.source` is HealthSnapshot. SCR01.S3 says a stopped service shows no Running badge, and STB03 step 3 says Starting becomes Running only when ready. Every one of the eleven screens repeats the identical chip string with the identical revision although their depicted states differ, so the chip is a static template rather than a snapshot-bound element. Requirement 2 demands an honest running-status AppBar and notification. The one screen whose purpose is to deny fabricated readiness fabricates it.

- **P3-03. The ARC target listener has no owner surface.** Requirement 4 separates the controller UI and ARC client from the target listener, router, auth and adapters. SCR07 is controller-only, with subtitle `Controller: selected compatible target`. The only other ARC text is the SCR08 card `ARC profile / Disabled until owner enables it / Bearer secret protected; raw TCP is not TLS`, which never says whether it configures the outbound controller or the app's own inbound listener. No screen shows a bound listener port, bearer rotation, inbound controller sessions, or which roots are exposed. The STB02 boundary promises protected owner surfaces are never an ARC root, yet no surface lets the owner see what is a root. Requirement 12 lists ARC among required screens, and half of the ARC design has none.

- **P3-04. The storyboards never depict the external agent.** The deck title slide at `design-c4/storyboards/storyboard.md:13` promises `explicit external-agent triggers`. All steps in `design-c4/docs/ui-asset-manifest.json` under `storyboards[*].steps[*].actor` are `Owner`. STB01 step 2 reports `Agent registered via its own MCP session` as the result of an owner inspect action, which is a precondition dressed as an outcome. STB04 moves from approving a scoped pairing challenge straight to editing grants of an already paired client. The SCR11 Result card requires `No grant until exact owner-reviewed commit`, yet the client's proof presentation and that commit review are not panels, so the Pending to Paired transition is never shown. The pairing flow is the one place where the agent's action is load-bearing, and it is missing.

**Moderate**

- **P3-05. The templated action legend contradicts the actual controls.** Every SCR svg carries the footer `C01 primary · C02 cancel/secondary · C03 navigation (locked on SCR09)`. On SCR04 the C02 slot is `Save group mapping`, a commit. On SCR02 it is `Revoke credential`, a destructive protected action. SCR03, SCR06, SCR08 and SCR01 place `Edit local override`, `Export selected scope`, `Review pairing` and `Open subscriptions` in the cancel slot. STB03 step 1 and STB06 step 1 both give an alternate branch beginning `Cancel:` on SCR08, which has no cancel or discard control at all. Screens that hold drafts therefore specify no way to abandon them.

- **P3-06. States and storyboards reference affordances that have no control ID.** SCR02.S1 `No clients: pair locally` and the index at `design-c4/docs/ui-screens-and-storyboards.md:23` route to SCR11, but no control carries that action, and SCR11 is absent from the navigation rail. The non-empty SCR02 has no add-client control, so pairing a second client has no documented route. SCR03's subtitle `Search bindings, types, evidence` and SCR03.S1 `No matches: broaden query` imply a query input, a result list and pagination, none of which exist. SCR04's subtitle `Owner preview for selected MCP client/session` and SCR04.S1 `unassigned entries searchable` imply a client selector, a job-description input and a search, none identified. SCR07's `selected compatible target` has no target picker, and the SCR08 ARC card lists no endpoint or token fields. SCR08 depicts values but no toggles or fields for boot, address, port, origin policy or TLS profile, and STB06 step 2 needs a pairing code and port that nothing collects. SCR10.S1 `No catalog: import validated release` names an import that no screen or control triggers. SCR03.C02 opens an override editor promising `Preview dependencies and CAS before saving` with no screen for the editor or the preview.

- **P3-07. The phone layout is unspecified.** All eleven artboards are 1280 by 840 three-pane layouts with a left rail and a right annotation pane. The only narrow-form statement is the one-line footer `Narrow layout: same IDs, single pane`. For an Android Compose management UI the narrow layout is the primary layout, and the navigation pattern that replaces the rail is not stated.

- **P3-08. State variants are labels, not specifications, and branches collapse.** Each state is a one-line box in the right pane. Only SCR07.S4 says which control changes enablement. The SCR09 locked rail differs from the others only by its aria label, with no disabled styling specified. Every storyboard panel has one `Success / transition` line and one `Error / cancel branch` line, so error and cancel are merged although requirement 12 names them separately, and several lines pack two branches, for example STB03 step 2 `Dismiss/timeout: deny; conflict: reload SCR08`. Alternates are text only, with no panel, arrow or state link. The counts below show how much of the declared state space the storyboards never visit.

| Screens | 11 |
| Non-S0 state variants declared | 36 |

The unexercised controls are SCR01.C02, SCR03.C01, SCR04.C02, SCR05.C02, SCR09.C02, SCR10.C01 and SCR11.C02. SCR05.C02 is the only route to the cancellation that STB01 is named for.

- **P3-09. SCR07 has no frame or tree viewport.** The screen is four status cards plus buttons. Requirement 4 covers mouse, wheel, key and text input and a Compose tree and frame adapter, yet the controller screen specifies no frame viewport, no tree view and no way to acquire pointer coordinates, even though the Input card says DIP scale is pinned. The manifest describes C04 as `Send typed input`, which leaves pointer input unexplained. The right pane line `SCR07.C01 / C02 / C03` omits C04, and the enabled-state label of C04 and the S4 relabel of C01 as a frame refresh are unspecified.

- **P3-10. Storyboard control sequences skip the steps that matter.** STB01 goes from SCR05.C01 inspect directly to SCR09.C01 approval without the SCR05.C02 press that opens the review. STB04 step 3 says `Draft rule/scope opens protected review` and then jumps to revocation, so the grant edit is never approved or shown committed. STB05 step 3 reports `Fresh protected review before export` with no SCR09 panel, unlike every other protected flow. STB03 step 2 ends on SCR09 and step 3 begins on SCR01 with no stated navigation.

- **P3-11. Which mutations are protected is inconsistent.** SCR08.C01, SCR03.C02, SCR02.C01, SCR02.C02 and SCR06.C02 route to SCR09. SCR04.C02 `Save group mapping` has a CAS conflict state, SCR04.S3, but no protected review statement, although group mappings are versioned catalog data under requirements 5 and 8. STB03 step 1 says `Protected change opens SCR09`, implying unprotected settings exist, without saying which.

- **P3-12. Pending approvals have no surfacing mechanism when the UI is closed.** SCR02 shows `binding.invoke / Ask`, so a tool call can block on SCR09. The persistent service runs without the UI, yet the notification's content and actions are never specified, and nothing says how an owner learns of a pending approval or how two concurrent Ask requests are queued while navigation is locked. The SCR09 `Bridge-owned remote input paused` card does not say what happens to in-flight ADB input tool calls from other clients during the pause.

- **P3-13. SCR05 retention semantics do not reconcile.** The Retention card says `Overflow default closes delivery with reason`, and SCR05.S2 says `Cursor expired: show retention boundary`. If the default overflow policy closes delivery instead of evicting events, an unread cursor can never fall outside the window, so S2 can only arise under an unnamed non-default policy or an unstated time-based eviction. SCR05.S3 names orphaned subscriptions without any lifetime bound, and nothing in this group says how a client learns that the owner closed its subscription.

- **P3-14. Several owner operations have no mechanism.** Catalog import has no screen. Log retention and quota configuration appear on no settings card, yet SCR06.S3 reports a `Disk quota` error. SCR06 calls the audit `Minimal mandatory audit`, but the behavior when that mandatory write fails, fail-closed admission or continue, is unstated. `Export selected scope` names no destination such as a share sheet or document picker.

- **P3-15. The chip and dashboard do not match the declared HealthSnapshot.** The manifest declares five fields under `shared_status.fields`, but every chip renders one state plus a revision, and no screen says which fields the chip or the notification show. SCR01 has cards for MCP, ADB, device view and active work but none for catalog readiness.

**Minor**

- **P3-16.** Storyboard actions relabel controls: SCR05.C01 becomes `Inspect subscription status` and `Inspect closed delivery`, SCR07.C01 becomes `Observe capabilities/frame`, SCR01.C01 `Start / Stop service` becomes `Observe listener readiness`, and SCR02.C02 becomes `Request credential revocation`.
- **P3-17.** All twenty-four STB panels repeat the placeholder `Selected client/session or exact target scope`, including panels for the dashboard and settings where no client scope applies, and no panel depicts the state variant it names.
- **P3-18.** The visible grant vocabulary is `Ask`, `Denied` and `Available`. No screen depicts an allowed or granted state, and `Denied` serves as both a policy mode on SCR02 and a status on SCR04.
- **P3-19.** The index at line 3 reads `with48dp`. ARC protocol naming varies between `arc-protobuf-v1`, `wire 1.0` in SCR07 and `ARC v1` in the STB02 boundary, and the package version distinction from requirement 4 is not surfaced anywhere in the UI.
- **P3-20.** SCR06's `other clients isolated` is ambiguous on an owner screen that sees all clients.
- **P3-21.** Text is editable `text` elements with a DejaVu Sans dependency and manual wrapping. Overflow cannot be checked without rendering, so I make no claim either way.

`★ Insight ─────────────────────────────────────`
A status surface that is supposed to be honest should be a function of one data source, not a decoration repeated per artboard. The design already has the right abstraction, a HealthSnapshot with a revision, and the right principle, desired versus actual state. What is missing is a failure-state artboard rendered from that abstraction, which would have made the SCR10 contradiction impossible to draw.

## Cross-artifact questions for other passes

- **Q1, coverage.** The manifest's `canonical_sources` and the index line 3 both declare `ui-svg` canonical and `docs/screens` a generated copy, yet no `design-c4/ui-svg` file appears anywhere in the global coverage index. The final verdict cannot claim canonical-source coverage until that directory is assigned, or the checksums file in group 1 is shown to bind it.
- **Q2, receipt.** `design-c4/build/receipts/storyboard-browser-validation-v5.json` must be read against P3-01. If it asserts the slideshow renders screens, the receipt is wrong. Group 1 should also identify which Gradle task inlines SVG data URIs into the deck.
- **Q3, pin.** Confirm marp-cli 4.2.3 against `design-c4/tooling/marp-package-lock.json`.
- **Q4, requirement IDs.** Confirm FR-KT-01, FR-KT-02, FR-KT-03, FR-DEV-01, FR-GRP-01 to 03, FR-CB-01 to 04 and FR-ARC-01 to 04 exist in the design document with meanings that match the screens tagged with them.
- **Q5, owner authority in one process.** SCR09 claims `No UI or JSON assertion can create owner authority` and `Fresh local owner authentication`. The UI and service share one package and process under requirement 2, so the design document and the OwnerTransition dynamic view must show the mechanism by which the service verifies approval independently of the UI, for example a user-authentication-bound Keystore key signing the command nonce. This group only states the principle.
- **Q6, HealthSnapshot.** The Startup dynamic view and design document should define the service_state enumeration visible here as Starting, Running, Stopped and Error, the five snapshot fields, and the notification content.
- **Q7, callbacks.** The CallbackFlow view and design document must reconcile P3-13: overflow policies, cursor expiry causes, orphan lifetime, and client-side signalling of owner-initiated close.
- **Q8, ARC.** Verify `arc-protobuf-v1` against `design-c4/docs/arc-protocol-contract.json`, and have the ArcSession view state which side releases a pressed input on disconnect and over which socket, given one request per socket.
- **Q9, MCP client pairing.** The design document must define the pairing contract that SCR11 labels `client key`, `TLS profile` and `One-time nonce`, including how a loopback TLS listener's identity is trusted by a paired client.
- **Q10, Android limits.** SCR08's `Unlock and eligible foreground start required` is honest but names no foreground service type and no version-specific boot-start exemption. I report this as unknown, not as a platform error.
- **Q11, byte identity.** Confirm `design-c4/docs/checksums.sha256` covers the generated screens, the canonical sources and the copies embedded in the HTML.
- **Q12 and Q13, policy classification.** Confirm whether group-mapping saves and each settings category are protected commands in the canonical policy model, resolving P3-11.

`★ Insight ─────────────────────────────────────`
When UI and service share a process, the sentence "the UI cannot bypass the service" is a claim about cryptography or kernel boundaries, not about code structure. Package-private Kotlin visibility stops accidental calls, not a compromised UI. The design document is where that boundary has to be made concrete, which is why Q5 is the most consequential open question this group raises for the whole-design verdict.
