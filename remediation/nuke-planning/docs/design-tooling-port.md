# Native NUKE design-tooling port proposal

Status: planning only. This document proposes the documentation portion of the one-application C# NUKE migration. No implementation, old Python, custom CJS, Node, Marp, Gradle build, browser launch, device operation, install, deployment, credential change or publication-checkout change was performed for this plan. The saved fixtures are observations, not C# parity results. This proposal must be reconciled with the parent plan and current effective MCP requirements before implementation approval.

## Evidence and boundaries

The [saved fixture inventory](saved-fixture-inventory.json) pins the inspected canonical inputs, all 221 current documentation SVGs, 107 ordered storyboard step tuples, and 58 Python test method names across the design and factoring suites. Its source hashes establish the baseline used here. The count is not a claim that all project Python tests have been inventoried; catalog/source-fact and publication tooling belong to the parent migration inventory.

The baseline has 11 screen definitions, 88 controls, 76 states, six storyboard composites, 107 step panels, and 108 slideshow sections including the cover. The 221 SVG files under `design-c4/docs` consist of 15 native Structurizr views, six UML code views, 17 screen/storyboard overviews, 76 state panels and 107 step panels. The additional 17 `ui-svg` copies are existing editable-output compatibility projections, not additional unique design views.

Relevant saved receipts are `build/receipts/gradle-package-040.completion.json` (221 outputs and no Android app), `reproducibility-008.json`, `design024-inline-ui-browser.json` (108 slides, 107 embedded step panels and 76 state checks), `design024-final-visual-inspection.json` (nine individually inspected contact sheets), and `design024-final-architecture-browser.json`. Their hashes are pinned in the inventory. These are legacy-toolchain evidence. Earlier `storyboard-browser-validation-v7.json` and `reproducibility-003.json` describe older denominators and must not be linked as current port acceptance evidence.

The canonical sources remain Markdown UI blueprint v2, Structurizr DSL, editable Markdown PlantUML class blocks, the module ownership DAG, and pinned API/schema contracts. The Kotlin server and Compose UI stay design only. This work does not claim Android runtime behavior, full Android API inventory completeness, or a deployed app.

## One application and one graph

All services below are ordinary internal C# types compiled into the parent's sole NUKE executable. They have no CLI, `Main`, standalone executable, script dispatcher or separate production project. They share the parent's workspace, artifact, process, hashing, receipt and operation-registry infrastructure. Test providers are loaded by the same application's test operation; they must not require an additional app entrypoint.

Expose one documentation generator category target, `Design`, with a singular typed `--operation` selector. Proposed operation names are `Architecture`, `Assets`, `Storyboards`, `Factor`, `Reconstruct`, `Manifest`, `Package`, `All` and the compatibility transport `GradleCompatibility`. These are category activities, not an old-script-to-target mapping. `Factor` and `Reconstruct` take the same validated snapshot and mapping parameters through typed options. `All` means the offline generation, validation, QA and packaging closure, not online acquisition or arbitrary historical-snapshot factoring. Public checks belong to the parent's central `Validate` category: `Validate --operation Design` invokes the complete required design/output/browser checks, and `Validate --operation Toolchain` owns toolchain checks. Generator prerequisites call the exact same validation services and private graph steps. There is no competing `Design Validate` or public `Design BrowserQa` entry. Acquisition belongs to the parent's canonical dependency/bootstrap category and is never an offline dependency.

One typed `OperationDefinition` registry owns category, operation, aliases, legal options, input contracts, private prerequisite IDs, service binding, effect classification and help text. It produces dispatch, preflight, dry-run output, compatibility alias metadata, help, generated operation documentation, parameter tests and target-DAG checks. There is no second operation list in Gradle, README, tests or a script. The registry is build-tool metadata, not a competing copy of UI behavior or module ownership.

The internal graph contains named steps; these are not public NUKE targets:

1. `ReadInputs` loads canonical documents and lock files once into immutable typed records and records their exact byte hashes.
2. `ValidateInputs` checks schema, identities, ownership, references, closed domains and source pin freshness.
3. `VerifyRenderEnvironment` validates required installed tools and digests for the selected operation, without acquisition.
4. `ProjectUi` depends on validated inputs. It creates the manifest, overview/state/step/composite SVGs, generated UI reference, storyboard Markdown, and only the marked navigation region in the main design Markdown.
5. `ValidateCrossArtifacts` depends on validated inputs plus projected UI, and checks the canonical protocol/model/UI relationships.
6. `ExtractCodeViews` extracts exactly the six named Markdown PlantUML blocks. `RenderCodeViews` depends on extraction and render environment.
7. `ValidateDsl` depends on cross-artifact and module checks plus rendered code-view images, because DSL image views reference those images.
8. `ExportNativeViews` depends on validated DSL. `RenderNativeViews` depends on exported PlantUML and the verified renderer. Rendering profile injection is idempotent and cannot change semantic model edges.
9. `RenderDeck` depends on projected UI. It uses the native C# deck service, not Marp.
10. `VerifyOutputs` depends on UI, native/code diagrams and deck. It checks exact path sets, vector structure, embedded bytes and all local links.
11. `BrowserQa` depends on verified outputs and a separately verified available browser. It does not run on missing or stale artifacts.
12. `Manifest` depends on verified outputs. `Package` depends on manifest and the required real QA gate. Package content and portable validation receipts come from the same artifact catalog.

`Architecture` selects steps 1, 2, 3, 4, 5, 6, 7 and 8. `Assets` selects 1, 2 and 4. `Storyboards` selects 1, 2, 4 and 9. The central `Validate/Design` operation selects the complete generation and verification closure through step 11. `Manifest` includes verification plus step 12's manifest portion, and `Package`/`All` include required browser QA and its package portion. `Factor` and `Reconstruct` are isolated read-only-input flows described below. The global registry is the authoritative final representation of these edges; this list is the proposal to encode there.

The operation planner computes a stable topological order, detects a cycle before effects, and executes each private node once per invocation. It uses source/content fingerprints and verifies all expected outputs before reusing a result. A missing output invalidates the cache. Failed/skipped prerequisites cannot produce a successful downstream receipt. An output-root lock prevents simultaneous writers. Input hashes are rechecked before committing a staged output set; changed inputs fail the invocation without reporting a mixed generation as valid. Original source and saved fixtures are retained.

## Gradle compatibility

Keep Gradle 8.14.3 and existing task names as thin delegates. Preserve aliases for `verifyToolchain`, `validateModuleGraph`, `validateModelContracts`, `extractCodeViews`, `renderCodeViews`, `validateArchitecture`, `exportArchitecture`, `generateArchitectureDiagrams`, `generateUiAssets`, `renderStoryboards`, `verifyDesignDocs`, `generateArtifactManifest`, and `packageDesignDocs`. Alias metadata is projected from `OperationDefinition`. Each alias requests the appropriate operation/step closure from NUKE; Gradle does not own prerequisites, rendering, checksums, validation, packaging or tool installation. Old aliases needing a narrower closure carry a registry-owned compatibility request value, not an extra public target.

For an invocation selecting several legacy tasks, the adapter resolves the requested aliases through the registry and submits their union to the sole NUKE planner once. The public `--operation` remains singular: the compatibility bridge is the registry-owned `Design/GradleCompatibility` operation with a validated requested-alias list; aliases are data, not per-script public targets. Its closure is exactly the requested union, never a silent broadening to `All`. The adapter is a thin request transport with no dependency decisions. The adapter must reject Gradle-side offline/parameter values that cannot be faithfully translated. Tests compare the selected operation plan and failure exit between direct NUKE and each Gradle alias, including the combined legacy command in the current README. If the parent selects another generic compatibility bridge name, it must reference this same canonical operation ID rather than introduce a second planner.

## Internal service seams

`DesignInputReader` returns a `DesignSnapshot` with source bytes/hashes, parsed blueprint, schema/API records, DSL/code views and module ownership. Exactly one parser extracts `ui-blueprint-v2`; generated manifest input is never substituted for canonical behavior. A formal blueprint schema validates all currently present fields without discarding extensions silently. Duplicate JSON keys, duplicate IDs, missing markers and unsupported schema versions are explicit failures. The approved schema becomes the shared validator/model contract; test fixtures do not introduce another production schema.

`DesignInvariantValidator` checks module classes and per-view explicit endpoints, domain-port ownership, permitted edges and cycles; source-pinned native signatures; C4 component mapping; dispatch, revocation, lifecycle and protected-owner sequences; API routes, bearer semantics and pinned copied contracts; and concrete control/state/step relationships. Preserve every legacy assertion, error case and interaction. Replace fragile keyword-only checks with structured checks where that preserves the observable rule, while retaining named regression fixtures for the exact old defects. Do not weaken a failing legacy rule merely because a structural parser is different.

`UiProjectionService` projects overview, state and focused-step panels from the same typed screen/state/control objects, using one XML escaping, text wrapping, typography and status-chip implementation. Health rendering combines the canonical example and state override using the baseline semantics, including integer revision, independent health facets, Stopped state and `Paused/OWNER_CHALLENGE`. Hardcoded state-ID special cases in the old renderer are migrated into approved declarative state data only after fixtures prove equivalent values; they must not remain duplicated between C# and blueprint. Projection errors precede writes. Generated navigation markers are required exactly once and all text outside them remains byte-identical.

`ArchitectureRenderer` shares the parent's typed process runner. It extracts editable PlantUML class blocks, runs pinned Java/PlantUML and Structurizr CLI with argument arrays, checks exit status and expected output identity, pads vector canvases, removes stale renderer source metadata and preserves text. It must use local resources only. The Structurizr workspace and six image-view relationships remain intact. No public renderer, workspace upload or network service is introduced. Process stdout/stderr, command, input hashes, executable identities and output hashes are retained in receipts.

`DeckProjectionService` projects both editable Markdown and standalone HTML from an ordered `DeckModel` derived from the storyboard objects. The current Marp CLI 4.2.3 and Node 26.8.2 profile conflicts with the no-Node rule. Retire Marp execution and its npm cache requirement. Preserve cover, 16:9 layout, 107 ordered actor/state/action/branch/success/error/cancel/next panels, 107 exact embedded SVG bytes, pagination, keyboard previous/next/home/end, hash navigation, visible current-slide state, print behavior, and finite navigation at both ends. External events remain observations. Inline browser JavaScript, if needed for navigation, is delivered product content with no Node build or script-tool runtime; its allowance must be confirmed by the parent scope decision below. No third-party web font, remote CSS, image or script may be fetched.

The new HTML deliberately has its own renderer identity. Its bytes cannot match Marp HTML. Acceptance compares the full content/interaction/layout contracts, then requires byte-identical repeat output under the newly pinned C# renderer profile. Do not claim a regenerated Marp lock or old HTML SHA proves the replacement renderer. Keep the existing Marp license/provenance where required for retained material; remove obsolete executable dependencies only after approved cutover.

`BrowserQaService` uses native .NET WebSocket/CDP and a pinned available Chromium-family browser, with a fresh task-local profile and loopback-only debugging endpoint. It owns and closes only its process/profile. It captures all 108 slides, checks all 76 states and 21 architecture SVGs, verifies decoded embedded bytes and vector text bounds, navigation and no external requests. Screenshot/contact-sheet bytes are QA evidence, never replacements for editable vector deliverables. Use a native .NET image dependency already selected and pinned by the parent for contact composition, or retain individual screenshots until one is approved. Browser/OS/font variation must be identified in receipts rather than sold as cross-platform pixel equality.

`LosslessEvidenceService` ports factoring and reconstruction within this same executable. It reads a frozen input manifest, verifies every referenced hash, replaces only canonical padded RFC4648 SVG data URIs whose decoded bytes exactly equal supplied SVG assets, retains unknown/malformed/noncanonical literals, records byte offsets and hashes, and reconstructs the entire original HTML byte-for-byte. UTF-8, repeated references and adjacent URI boundaries are required fixtures. Inputs remain untouched; an existing output directory is rejected. Path traversal, reserved-reference collisions, changed map/view/asset, ambiguous duplicate mappings and unknown reconstruction tokens fail explicitly rather than producing unverifiable evidence. The mapping is a derived review view, never omitted content or reduced design scope.

`DesignPackageService` shares the parent's artifact catalog, canonical relative-path rules, SHA256 service and deterministic ZIP service. It sorts ordinal normalized relative paths, fixes archive timestamps, avoids self-hashing, rejects duplicate/case-colliding names and path escape, and verifies the package after writing. Preserve the current portable docs/SVG/DSL/PlantUML/API/wrapper/lock/notices shape and concise path-free validation receipts. Replace retired Python/CJS sources with the sole NUKE source/runtime invocation contract appropriate to the approved package mode. Exclude caches, source catalog data, reviewer streams, historical outputs, screenshots, Word/PDF, live credentials and machine paths. Tests verify exact allowlists and exclusions from one catalog, not two hand-maintained lists.

`ToolDependencyService` replaces bootstrap download/hash/extraction behavior using the parent's `HttpClient`, hash and archive services. Retain exact Gradle 8.14.3 checksum/wrapper identities, PlantUML 1.2025.10, existing Structurizr CLI 2025.11.09 digest and JDK 21.0.8 renderer profile. Native .NET SDK 10.0.403 and NUKE 10.1.0 are parent-brief observations to be verified in the parent toolchain inventory. Do not invoke npm or Node. Reject unpinned downloads, size/hash mismatch, unsafe ZIP entries, symlink escape and partial cache files. Offline mode performs no acquisition or network attempt, and fails with the missing pin list. The old separate extracted Gradle distribution versus official wrapper cache distinction must remain explicit in preflight and documentation. Future bootstrap execution is separately authorized, not part of this planning run.

## BDPv4 gates and cutover

First capture or reconcile the parent FR/TR/AC records and use the linked [AC-to-test specification](ac-to-test-specification.md). The local DOC-AC identifiers are proposal anchors, not invented persisted MCP requirement IDs. Requirement creation and definitive FR/TR/TEST mapping remain the parent owner's responsibility.

For each small service increment, implement the contract tests, deterministic independent mocks and negative controls first. The mocks provide canonical bytes, process results, clock values, browser protocol responses and storage failures through the intended seams. Run every case with correct fixtures, deliberately broken responses and required interactions; the harness passes only when expected negative controls are rejected. A green mock receipt with zero failed/skipped/unexecuted cases precedes the first production edit for that increment. Bind the same assertions and fixtures to real services, preserve expected values and run the complete applicable suite. No red stub, legacy success receipt or mock-only result authorizes the next production slice.

Suggested increments are: input/registry/preflight; validators; UI projections; local architecture rendering; native deck; native CDP QA; factoring/package; and compatibility cutover. Freeze per-increment test manifests and hashes before implementation. Gates record exact NUKE invocation, source/fixture hashes, provider mode, ordered case IDs, correct/negative-control denominators, zero skipped count, TRX and full logs. Parent integration runs the complete application unit suite and all design integration/browser lanes before the final cutover. Required independent hostile review receives the actual TRX files and receipts and does not build or run tests itself. No done claim before the parent's required AGREE and score gate.

Cutover changes are intentionally breaking for direct `python`, custom `.cjs`, npm/Marp and Python-unittest invocations. Native NUKE category commands and existing Gradle aliases are the supported replacement. Do not delete original files during this planning task. During approved retirement, copy and hash-verify original tooling into the approved retained history location and obtain operator clearance before any original deletion. Generated package/checksum documentation must refer only to approved active tooling. Rollback is an explicit return to the saved artifacts/tooling by operator direction, never automatic execution of forbidden runtimes.

## Locked decisions and remaining integration proof

1. Native slideshow runtime is locked: browser-only inline JavaScript is permitted as delivered HTML content. The native projector implements navigation without Node/Marp. Actual browser navigation/layout proof remains a separate gate.
2. Portable package mode is locked to source/build configuration for the sole NUKE application. No additional executable app is introduced. The editable generated SVG/HTML remains self-contained; package execution/provenance must be verified before distribution.
3. The operation selector is singular. `Design/GradleCompatibility` accepts a validated alias list and the central registry computes one private-step union. The actual thin Gradle adapter and its real equivalence tests remain pending.
4. The first QA host is the current LAB Linux environment. Missing browser/fonts fail with exact prerequisites. Cross-platform byte/pixel equality is not claimed until separately proven and profiled.
5. The existing state `health` field represents all twelve implicit legacy overrides. Their minimal canonical data migration is complete, with original copy/hash, dual CJS/SVG verification and unchanged other fields/text recorded in `health-migration-and-gate-chronology.json`. Independently edited manifest fixtures preserve the exact source delta. No new schema version or state behavior was introduced. A formal full-input schema validator remains future validation work.

These are explicit design/distribution decisions, not evidence that existing docs fail. No reviewer/API-surface completeness analysis is included in this subtask.
