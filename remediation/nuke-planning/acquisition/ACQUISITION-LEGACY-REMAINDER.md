# Acquisition caller responsibilities after the native Fetch baseline

The proven baseline covers locked recipe projection, raw/hash/Git/base64 verification, bounded full ZIP and version-pinned metadata ranges, immutable bundled snapshots, exact target/sealed resume, C# cache identity/strict-derived receipts, explicit historical cache import and the actual Sources/Fetch CLI. It does not establish complete legacy caller/option parity.

- `tools/rehydrate.py:402` plan/default recipe selection: this increment supplies the pure Plan CLI and retained native manifest. Legacy release-to-default-recipe/workspace discovery remains a caller decision; the native CLI currently requires explicit project/recipe/lock/output roots.
- `tools/rehydrate.py:224,232` producer_path/doctor: native code and parser/runtime/tool pins must be admitted through existing native services. Old Python minor/package/Expat checks remain historical evidence, not executable dependencies or a claim that C# cache identity equals Python identity. This needs an explicit native doctor/caller contract if exposed.
- `tools/rehydrate.py:258,272,434` inventory binding and seed: seed's ordered local_path/required_snapshot candidate lookup plus imported/reused/absent counters and persisted recipe-bound working inventory are not the same operation as Fetch's required-snapshot import. Root owns seed dispatch; Acquisition supplies shared pin/store verification and copying while retaining originals.
- `tools/rehydrate.py:277` extract: parser-to-SourceCache orchestration, source-kind/platform target context, strict-cache-bytes frontend and regenerated-difference counters remain a composition responsibility shared with Sources' pure parser owner. Existing SourceCache/HistoricalSourceCache engines are reused; no second Java/SDK parser or old producer execution is needed.
- `restore_snapshot.py:60` batch archive reuse: the old caller caches selected metadata and opened source archives once per archive URL. Native raw-path/whole-archive byte caching is present, but distinct selected members currently reopen/re-read range metadata per member. Batch interaction parity requires explicit immutable archive/version-key reuse, without merging incompatible ETag/hash/profile pins.
- `fetch_snapshot.py:9` and `restore_snapshot.py:60` status/downloaded + Git-blob grouping, default dry-run `--download` selection and missing counters are inventory-oriented callers, separate from locked physical-path Fetch. Generic rehydrate's configurable `--delay` after newly downloaded sources and explicit `--allow-file` fixture frontend are also not exposed by the current native Fetch CLI; core transport profiles and fixture seams remain reusable.
- `tools/rehydrate.py:354` build/validate/export and sealed result-file checks belong root/Catalog dispatch. Acquisition hands over pinned raw/cache identities and recipe context; it does not duplicate database generation, catalog validation or permission export.

Observation from the read files: canonical fetch/restore use `--download`; generic `rehydrate.py` exposes no `--resume` or `--no-resume` flag. Native `RehydrationPlanRequest.Resume=false` already has a tested core contract, but exposing a NoResume CLI control is a native extension, not a literal flag parity claim for those three files.

This mapping is based on actual function/caller reads, not basename/hash inference. It requests no extra test expansion or network/corpus run and claims no tracked whole-project completion.
