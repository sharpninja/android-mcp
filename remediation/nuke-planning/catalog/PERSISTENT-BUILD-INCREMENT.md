# File-backed retained staging and streamed exports

This is a follow-on to the bounded seven-case native CatalogBuild increment, under FR-BUILD-004 and TEST-BUILD-004/007. The initial increment uses an in-memory SQLite database and materialized export byte arrays. It is not the full historical producer/scalability port.

The root owns the additive shared `IStreamingArtifactStore.WriteStreamAsync(relativePath, mediaType, Func<Stream,CancellationToken,Task>, ct)` seam and the one shared FileArtifactStore implementation. Catalog does not copy its transport, path, lease, hash, identical-existing or retained-partial rules.

Catalog owns `CatalogDatabase.CreateFile`: read and validate prerequisite schema files first; create a new retained file, never overwrite an existing stage; open SQLite on that file; run the same schema sequence as the existing in-memory factory. The same staging factory supplies the build pipeline. No extra schema or per-profile producer algorithm is introduced.

The production build must keep the imported records and projection indexes in its file-backed staging database, enumerate SQLite cursors for exports, and write through the shared streaming store. Each output write is bounded to at most 65536 bytes. The closed retained staging database is the source for the final streamed, byte-verified catalog.sqlite marker. Originals are never moved or deleted. This changes memory behavior and staging observability; full legacy declaration/annotation/unknown-concern parity remains separately pending.

`CatalogPersistentBuildCases` pins four mock-first scenarios: original ten-entry fixture, duplicate source occurrences with the same ten entries, failure partway through inventory export, and populated-output refusal. The harness checks thirteen observations individually, including reopened retained-stage rows, a closed database at final-copy admission, final/stage byte agreement, nineteen stream calls on success, no buffered artifact writes on success, bounded writes, absence of a final marker on failure and a retained incomplete export. Each observation has its own intentionally wrong response inside the passing mock harness.

The real provider will inject a stage factory returning the actual CatalogDatabase and a tracking decorator around the root's actual FileArtifactStore. It observes connection state when the final stream is admitted and counts actual stream writes. It independently reopens the retained database and compares final bytes/hashes. The stream-failure fixture throws from the injected output boundary after an actual partial write; the production service has no test-variant branches. No new production implementation is permitted until this mock gate passes and root acknowledges it.

The eight build mocks and ten file-factory mocks passed in the 245-test gate before their respective production changes. The file factory now has five passing native cases. The first streaming build implementation and same four real bindings are staged outside the app after the shared store's native gate. It streams SQL table/document cursors and offline aliases through the shared store and retains the actual closed file-backed database as final-copy source. It still holds source extraction results, declarations and projection collections during import. Those collections need a separately gated input/projection cursor refactor. Bounded output writes do not establish bounded whole-producer memory, and no such claim is made.
